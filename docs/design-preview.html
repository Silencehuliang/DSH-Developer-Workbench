在 DSH 里长出一个
开发工作台

左侧「新会话」下方、「插件」上方新增一个入口；点开后是绑定本地项目的开发工作台。 它用 Matt Pocock 的 27 个技能当阶段引擎，用磁盘产物推导当前进度， 把「下一步」连同完整上下文派发给对应的工作区会话 —— 管流程、管交接，不跟你抢会话。

形态 profile 插件（宿主 + 浏览器双半身） 依赖 零构建 · 零第三方包 定位 控制台（不自己跑 agent） 页面 单文件 HTML 设计稿

01 · 一页看懂

六个关键点

先说结论：位置是精确可控的，客户端半身可以手写、不需要打包工具，工作流状态从文件推导而不是靠人手点。

📍 入口位置精确可控

侧边栏顶部顺序是「品牌 → 新会话 → 全局面板列表 → 工作区 → 设置」。内置「插件」页注册的排序值是 0，我们注册 -10 就必然落在它上方、新会话下方。

🧩 零构建客户端

所有官方插件前端都是同一种 window.__ModuleLoader__.load() 手写格式。基线只提供 react 等少数模块，因此不需要 tsdown / vite，没有依赖安装。

🎛 控制台，不是执行器

工作台不自己创建 agent 干活。它负责看清状态、决定下一步、生成带上下文的技能指令，然后创建/复用工作区会话并发送，再跟踪结果。

🗺 阶段 = 产物的函数

是否有 spec、工单、评审记录，直接决定当前阶段。所以「下一步」是确定性的、可以解释为什么，而不是一个要你手动维护的状态。

🤝 交接有落点

每轮回答结束后在会话里出现一个动作行；「推进」会打开派发确认框，提示词可编辑，发送后自动跳到那个会话。

📦 技能随包内置

Matt 的 27 个技能随插件包分发（MIT + 署名），可离线安装到 <项目>/.agents/skills，一份安装同时被 Claude Code / Codex / Copilot 识别。

04 · 阶段即状态

工作流管控的核心：读磁盘，不靠人手填

下面是阶段推导链路。左侧是判定依据，右侧是这一步调用的 Matt Pocock 技能。状态是算出来的，所以可以随时解释、可以重算、不会漂移。

阶段判定依据（磁盘事实）对应技能派发出去之后会发生什么
setup一次性项目里没有 tracker 声明setup-matt-pocock-skills确定 issue tracker、triage 标签词汇、领域文档布局，之后所有阶段都按这套约定走
grill还没有 spec 产物grilling · grill-with-docs对方案做一轮拷问，顺手产出 ADR 与术语表，把没想清的地方逼出来
spec没有成稿的 specto-spec把对话综合成 spec 并发布到 tracker，不做二次访谈
tickets.scratch/<feature>/issues/ 为空to-tickets拆成 tracer-bullet 垂直切片，每单一个文件并声明 Blocked by 依赖边
implement存在未完成工单 → 取 frontierimplement · implement-spec · tdd实现「所有阻塞都已解除」的那张工单；测试优先时叠加 tdd
review工单全部完成，无评审记录code-review按「规范」与「是否实现 spec」两条轴并行走查，并排给出结论
pr评审通过pr撰写 PR 正文
retro已提 PRretro对这次会话做复盘
旁路工作量超出单会话承载wayfinder先在 tracker 上铺一张决策地图，逐张解决到路线清楚为止
交接任意阶段收尾handoff把当前会话压缩成交接文档（含「下一个 agent 该调哪些技能」），落到系统临时目录
为什么要有「旁路」

Matt 的流程里 wayfinder 专门处理「一个会话装不下」的大块工作：先在 tracker 上把决策问题铺成地图，逐个解决。工作台检测到工单爆炸或 spec 超出规模时会主动建议走它，而不是硬塞进 implement。

为什么要有「交接」

上下文窗口是硬的。handoff 负责把当前对话压成文档、只引用已有产物（spec/工单/ADR）不重复内容，并列出下一个 agent 该调用的技能。工作台负责记住这份文档在哪、并把新会话接到它上面。

关键设计取舍：阶段状态不写死在人手维护的字段里，而是每次都从文件系统重新推导。人工可以覆盖（比如「我确实想跳过拷问」），但覆盖只是一层显式补丁，面板会标出「已被手动覆盖」，避免状态和历史脱节。

05 · 派发与交接

点「下一步」之后看到什么

不搞静默魔法：发送前一定给你看清楚目标、以及将要发出去的完整提示词，而且提示词可编辑。

▶派发：拆 tracer-bullet 工单✕
Developer Workbench~/projects/Developer Workbench
新建会话或选择该项目下已有会话继续
发送后自动跳到该会话，工作台继续跟踪阶段变化
①生成

宿主半身按「项目 + 阶段 + feature + 目标工单」拼出提示词：技能路径、产物路径、tracker 约定、triage 标签、完成时的回报要求。

②确认

面板弹出确认框，全文可改。这一步是刻意的：工作台永远不背着你把内容发进会话。

③送达并接力

创建/复用会话 → 以队列模式发送 → 跳转过去。会话跑完一轮，工作台重新扫描产物，阶段自动前进。

提示词的兜底设计：每一段提示词里都会出现技能的绝对路径，并写明「若 skill 工具可用则优先用它」。因为我现在实测到你 profile 里技能发现当前是关闭的 —— 这个写法让工作流在两种情况下都能跑通（详见第 11 节）。

08 · 包结构

一个目录，两个文件就是全部运行时

你的 profile 里已经把这个包挂上了：bundle 列表、依赖 junction、HMR 监听、数据目录配置项都在。所以补齐包体后大概率不用改 profile。

为什么零构建很重要：官方插件前端都是预打包产物，第三方要复刻那套还得配 tsdown。但 dsh-our-free-model 证明了手写 ModuleLoader bundle 是官方支持的路径，配合基线只提供 react 的约束，我们可以完全跳过打包工具链 —— 少一层依赖，少一类环境问题。

09 · 分期与验收

六期，每期都能独立验收

不一次性堆完再调。每期结束都有可点、可看、可复现的产出。

P0
骨架与接线先看见

建包体、profile 接线、验证 HMR 与客户端重载路径，主面板先渲染占位内容。

验收：点开左侧「开发工作台」出现面板，位置在新会话与插件之间，控制台无报错。
P1
宿主数据面看不见但关键

工作区与 git、产物扫描、工单解析、技能自检、阶段推导，全部挂上路由。

验收：对真实项目逐条 curl 出正确 JSON；工单 Blocked by 解析与阶段推导有单测。
P2
主面板界面主体

三栏布局：项目列表、阶段流水线、工单看板、产物预览、技能自检、Git 概览。

验收：真实项目上阶段与看板渲染正确，明暗主题跟随，键盘可达。
P3
派发与交接核心价值

派发确认框、创建/复用会话、发送提示词、自动跳转；交接文档列表与接力新会话。

验收：点「下一步」真的建出会话并送达提示词，页面跳到该会话，回来后阶段前进。
P4
会话侧入口与设置页打完收口

输入框下方环境栏、回答后动作行、悬停卡一行，以及设置页全部选项。

验收：环境栏只对已登记项目出现；设置项立即生效；未登记项目下三处均不渲染。
P5
打磨与端到端验收交付

中英双语、可访问性、README、自检脚本全绿，在真实项目上跑完整条阶段链。

验收：node scripts/*.mjs 全绿；README 能让人照着复现；整条工作流走通一遍。

10 · 风险与对策

四个已知风险，都有兜底

其中第一个是我实测发现的问题，也是唯一一个可能牵动 DSH 内部配置的地方 —— 但我不会让方案吊死在它上面。

已实测
技能发现当前是关闭的

我往项目里放了探测技能后用 skill 工具加载，失败；再试官方自带的技能（cordis-plugin-development 等 4 个），同样失败。说明不是路径问题，而是你 desktop profile 里文件系统技能提供方没有激活。

对策：① 派发提示词里永远给出技能的绝对路径，让 agent 直接 read 流程，完全不依赖那个工具；② 工作台的「技能自检」把这件事明说，而不是装作一切正常；③ 如果确认是 profile 层开关，我提供一键修复（改配置前先备份）；若需要改 DSH 内部我会如实告诉你，不硬来。
中等
客户端半身的热重载

宿主半身已被你的 HMR 监听覆盖；但「无构建」的客户端 bundle 改动后能否免刷新生效，需要实测。

对策：P0 专门验证并记录结论。最坏情况是改前端后手动刷新页面 —— 可接受，且我会在 README 写明。
中等
刚创建的目录可能被文件监听漏掉

技能目录如果是在会话运行中途才创建，监听器可能挂不上去（Windows 上目录时间戳不总更新）。

对策：安装完成后提示「下个会话生效」，并提供「重新检测」按钮，而不是让你以为是 bug。
低
不碰你的既有项目

你要求不参考本地已有项目（如 dsh-graph、dsh-workflow-kernel），我按此执行。

边界：工作台只读写「被绑定项目」的 .agents/skills、.scratch/，以及它自己的状态文件；对项目的写入全部走显式确认。

结论依据
入口插槽与排序官方文档原文：「Plugins add an icon component to the root-scoped sidebar.panellist list with an id, optional order…The same id addresses the component registered in the layout's root-scoped main keyed slot」；内置插件页注册 order: 0，外壳按 order 升序排序。侧边栏渲染顺序可从源码逐行确认（品牌 → 新会话 → 面板列表 → 工作区 → 页脚）。
零构建客户端所有官方 client.js 首行都是 window.__ModuleLoader__.load({ id, factory })；外壳只种入一张冻结的基线模块表 react / react-dom / react/jsx-runtime / cordis / dsh-client-store / dsh-client-ui-slots / dsh-client-ui-primitives / dsh-client-ui-dockkit。已安装的第三方插件 dsh-our-free-model 就是纯手写、无打包、只依赖 react。
派发能力SessionController 上带 @Remote 的方法包含 create / prompt / follow / page / rename / cancel；prompt 的请求体是 { requestId, sessionId, mode: 'queue'|'steer', content }。客户端另有 uiWorkspace.startSession / openSession / connectWorkspace。
文件读取需要会话作用域workspaceFiles.read 的第一个参数是 WorkspaceFileScope { sessionId, workspaceRoot }，由会话 id 反查。没建会话的项目读起来很别扭 → 因此文件与 git 放宿主半身。
技能发现根与格式五个根：<项目>/.dsh/skills(100)、<项目>/.agents/skills(200)、自定义(300)、~/.dsh/skills(400)、~/.agents/skills(500)；项目根取最近的 .git 祖先，没有就用当前目录。格式为 <name>/SKILL.md 或顶层 <name>.md，frontmatter 要求 kebab-case 的 name 与 description。
技能为何当前不可用技能注册表在宿主平面，而每个 agent 预设才挂载文件系统提供方与技能工具；web 外壳把宿主平面的这两行显式关掉了。实测：连随包自带的 4 个技能都加载不到，证明该提供方在当前会话作用域内未激活。
profile 已有接线profiles/desktop/package.json 的 dsh.profile.bundles 已含 dsh-developer-workbench，依赖为 link:…/Developer Workbench/plugin；cordis.patch.yml 已有 id: developer-workbench 的配置项与指向本目录的 HMR 监听；node_modules/dsh-developer-workbench 的 junction 已存在（指向目前为空的 plugin/）。
